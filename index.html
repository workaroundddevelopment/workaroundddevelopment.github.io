A methodology based on how software is actually developed, rather than how we pretend it is developed.

The Manifesto

We are uncovering better ways of developing software by doing it and helping others do it.

Through this work we have come to value:

Workarounds over solutions.
Production over architecture.
Deadlines over design.
Tickets over understanding.
Metrics over outcomes.

That is, while there is value in the things on the right, we value the things on the left more.

"It works."
— The highest form of architectural validation

The Principles

01

Make It Work

The first implementation is not supposed to be correct. It is supposed to work.

02

Don't Fix What Works

Every working system is a legacy system. Touching it creates unnecessary risk.

03

Move Complexity Somewhere Else

Complexity cannot be eliminated. It can only be moved to another team, another service, or another quarter.

04

Architecture Is a Future Problem

If the system is not experiencing the problem today, designing for it today is premature optimization.

05

Every Workaround Is Temporary

Especially the ones that have been running successfully for seven years.

06

Document It in a Ticket

If there is a ticket, the workaround is now officially part of the architecture.

07

Automate the Workaround

Once a workaround has been performed three times, automate it. This transforms manual debt into infrastructure.

08

Blame the Dependency

Distributed systems exist primarily so that someone else can be responsible for the failure.

What is a workaround?

A workaround is a solution that solves the immediate problem without necessarily solving the underlying problem.

workaround(problem) { return "something that works"; }

Unlike a bug fix, a workaround is optimized for time-to-recovery rather than long-term correctness.

This is not necessarily a bad thing.

In real software development, constraints are everywhere: deadlines, organizational boundaries, legacy systems, dependencies, budgets, incidents and, occasionally, decisions made by people who no longer work here.

The Reality

Software engineering literature often describes workarounds as deviations from the intended process.

In practice, workarounds can be rational responses to organizational and technical constraints.

The interesting question is therefore not:

"Why did the developer do this?"

but:

"What made this the most rational thing to do at the time?"

And perhaps more importantly:

"Why is the workaround still here five years later?"

The Laws of WDD

Law #1 — The Temporary Solution Law

Every temporary solution has a non-zero probability of becoming permanent.

Law #2 — The Dependency Law

The more services a system depends on, the more opportunities it has to explain why it cannot work.

Law #3 — The Ownership Law

A problem without an owner becomes an integration problem.

Law #4 — The Deadline Corollary

The closer the deadline, the more reasonable the workaround becomes.

Law #5 — The Success Paradox

The better a workaround works, the less likely it is to be replaced.

Research

WDD is satire, but the phenomenon behind it is real.

Research has examined the benefits and consequences of workarounds in software development projects, including situations where developers deliberately use workarounds to deal with organizational and project constraints.

Workaround Driven Development is an informal and satirical concept. It is not an established software development methodology, framework, certification or professional standard (yet).
